# NEXUS-Q Sign — Private-key custody

Date: 2026-11-13  
Status: initial implementation in Sign Core; filesystem persistence and security review pending.

## Product boundary

Sign owns its own identities and private keys. It does not use Vault sessions, Vault identity records, Vault storage, or Vault APIs. The shared `nexusq-core` dependency is a compiled Rust library used for cryptographic primitives only; it is not a shared service.

## Current implementation

The private crate `crates/sign-core` contains:

- ML-DSA-65 key generation and signing through `nexusq-core = 4.1.2`.
- ML-DSA-65 public-key verification.
- A password-derived encryption envelope for one 32-byte FIPS 204 signing seed.
- Argon2id v1.3 with 19 MiB memory, 2 iterations and 1 lane.
- XChaCha20-Poly1305 authenticated encryption.
- Fresh 16-byte salt and 24-byte nonce generated by the OS random source.
- Envelope header authenticated as AEAD associated data.
- Plaintext returned by decryption in a zeroizing container.
- No API that returns the private seed as plaintext to the UI.

Envelope layout (v1):

| Field | Size |
|---|---:|
| Magic NQSK | 4 bytes |
| Version | 1 byte |
| Argon2 salt | 16 bytes |
| XChaCha20 nonce | 24 bytes |
| Encrypted seed + authentication tag | 48 bytes |
| **Total** | **93 bytes** |

The format is private to Sign and is not the detached document signature format. The password is required to contain at least 12 bytes at the current API boundary.

## Filesystem storage implementation

`crates/sign-core/src/key_store.rs` now provides a ciphertext-only `KeyStore`:

- One fixed-size `.nqsk` envelope per 16-byte key identifier.
- Owner-only directory permissions (`0700`) and file permissions (`0600`) on Unix.
- Temporary file created with exclusive creation and a random suffix.
- File contents are flushed with `sync_all`, then atomically published without replacement in the same directory. Linux/Android use `renameat2(RENAME_NOREPLACE)` through the safe `rustix` API because Android app storage denies hard-link creation; other supported Unix targets use the hard-link no-clobber fallback.
- Parent directory sync after commit and deletion on Unix.
- Strict 93-byte NQSK v1 framing validation.
- Rejects a symlink/non-directory store root and symlink/non-regular key files.
- Refuses duplicate key IDs; replacement/key rotation is not implicit.
- The store accepts and returns ciphertext only; decryption remains in Sign Core.

The application must pass a trusted per-user app-data directory to `KeyStore::open`. The module validates the final directory component; it does not independently establish trust in every ancestor directory. Filesystem race resistance and platform-specific behavior still require review.

## Identity metadata

The initial NQID v1 public metadata store is implemented in `crates/sign-core/src/identity_store.rs`. It stores identity ID, independent key ID, display name, encoded ML-DSA-65 public key and informational local-clock creation time. It contains no private material and is documented in `IDENTITY_MODEL.md`. Version 1 deliberately models one active key per identity. This metadata is a local label/record, not a certificate or external trust assertion.

The identity metadata store and encrypted-key store are not yet coordinated transactionally. Tauri integration must handle partial creation and orphan recovery before exposing identity creation in the UI.

## Remaining storage work

1. Connect both stores to Tauri's application-data directory without exposing private paths to JavaScript.
2. Implement a Rust-owned identity lifecycle with crash recovery across encrypted-key and public-metadata writes.
3. Define identity deletion and password-change/rotation behavior, including crash recovery.
4. Add permission, symlink-file, crash-recovery and platform-specific atomicity tests.
5. Keep backups/export opt-in and explain that recovery depends on the user's password and backup of the encrypted envelope.
6. Avoid including passwords, seed bytes, ciphertext contents, or full private paths in logs and error messages.

## Threat model and limitations

This first design protects a key file at rest against offline reading without the passphrase, assuming the device and process are not already compromised.

It does not protect against:
- Malware or an attacker controlling the unlocked process.
- Screen capture, keylogging, memory inspection by a privileged attacker, or compromised OS.
- Weak/reused passphrases or loss of the passphrase.
- Rollback or deletion of encrypted key files.
- A compromised dependency or build supply chain.

Argon2id parameters are an initial baseline, not a final platform-wide performance decision. They must be benchmarked on supported desktop targets and adjusted without weakening the threat model. The format needs a versioned migration plan before release.

This is source-level confirmation, not a substitute for runtime memory testing.

- [ ] Add filesystem atomic-write, permissions, symlink and crash-recovery tests.
